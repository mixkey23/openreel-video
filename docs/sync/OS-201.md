# OS-201 — Contrato `sessionStorage['__framesmith_config__']`

**Estado:** ✅ prueba escrita y en verde sobre el fork actual · `apps/web/src/hooks/framesmith-init-contract.test.ts` (4 tests)

Fija lo que `useFramesmithInit` construye a partir de `FramesmithConfig` (`clips`, `episodeId`, `mode init|restore`, `music`):

1. Sin config → no hace nada (ni `fetch`, ni `addClip`).
2. **init:** crea 1 pista de vídeo + 1 de audio; los vídeos entran en su `start_time` (los de `url:null` se omiten); el audio por beat se **deduplica por `beat_id`** y se añade con **duración explícita** (`addClip(..., audioDuration)` como 4.º argumento) mientras que el vídeo se añade sin duración; cada media importado guarda `originalUrl`; se publica `framesmithEpisodeId`; el config se consume.
3. **restore:** `GET /api/episodes/{id}/s6/project` → re-descarga de cada `originalUrl` → `loadProject`; los items sin `originalUrl` no se tocan.
4. **restore fallido** (HTTP ≠ 2xx): reescribe el config con `mode:"init"` (fallback).

**Limitación honesta:** se sustituye `importMedia` por un doble (no hay WebCodecs en jsdom) y no se usa todavía el grabado real de `episode_035` (no está en el repo del fork); el criterio del backlog («alimenta el config grabado de `episode_035`») queda **parcial**. Los ficheros de música sí usan el fixture real `framesmith-music-feed.json` (OS-204).
Hallazgo durante la prueba: las dos pistas creadas seguidas pueden colisionar de id (`track-${Date.now()}`), ver OS-106 #8. La prueba fija el reloj para no depender de esa carrera.
